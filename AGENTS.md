# Конвенции репозитория

Единый свод правил для людей и для агент-сессий. Claude Code читает этот файл через `CLAUDE.md`
(`@AGENTS.md`), остальные агенты — сами.

Риск-сводка по синтетическому кредитному портфелю: CSV → PostgreSQL (сырой слой `raw`, витрины
`reporting.v_*`) → семантическая модель в YAML → статичный дашборд на Vega-Lite. Определения
метрик и их толкование — в README, разделы «Итоговые цифры» и «Как толкуются определения».

## Стек

- `sql/` — PostgreSQL 16, образ `postgres:16` в Docker. `psql` запускается внутри контейнера, на
  хосте он не нужен.
- `semantic/*.yaml` — модели в формате заказчика: `model`, `source`, `dimensions`, `measures` с
  типами `sum`/`avg`/`count`.
- `dashboard/` — Vega-Lite 5.21 и vega-embed 6.26 с jsDelivr, одна статичная страница.
- `scripts/` — bash и Python 3 только на стандартной библиотеке: venv и pip не нужны.
- `Makefile` — единственная точка входа.

## Команды

- `make load` — поднять контейнер `crs-pg`, перезагрузить `raw`, пересоздать витрины, прогнать
  `sql/90_checks.sql`.
- `make export` — `load` плюс выгрузка витрин в `dashboard/data/*.json`.
- `make verify` — только сверка JSON с пересчётом из CSV, база не нужна.
- `make serve` — дашборд на http://127.0.0.1:8765/. Из `file://` страница не работает: спеки и
  данные грузятся через `fetch`.
- `make screenshot` — перегенерировать `docs/dashboard.png`; нужны `google-chrome` и интернет
  (библиотеки берутся с CDN).
- `make psql` — консоль базы, `make down` — удалить контейнер.

## Ворота

Изменение считается готовым, когда прошло из корня репозитория:

```bash
make check
```

Запускать голой командой и смотреть **реальный код возврата**. `make check | tail` вернёт код
возврата `tail`, а не проверки; «зелено» без exit code 0 ничего не значит. Внутри рабочего цикла
хватает `make verify` (сверка по уже выгруженному JSON), перед коммитом — ворота целиком.

Предусловие — запущенный Docker daemon. Порт хоста не занимается. Контейнер `crs-pg`
переиспользуется между прогонами: если у существующей витрины поменялся состав или тип колонок,
`CREATE OR REPLACE VIEW` упадёт — тогда `make down` и снова `make check`.

## Инварианты

Эти свойства закрыты проверками и не ослабляются. Проверка, которая начала мешать, — повод
обсудить изменение, а не повод её переписать.

| Инвариант | Где держится |
| --------- | ------------ |
| Кредит встречается на дату один раз после схлопывания полных дублей | `sql/90_checks.sql:unique_loan_per_date`; `scripts/verify.py:load_loans` |
| Валютный кредит пересчитан по курсу ровно на дату среза | `sql/90_checks.sql:fx_rate_on_report_date`; `scripts/verify.py:compute` |
| На день и валюту — один курс | `sql/90_checks.sql:single_fx_rate_per_day`; `scripts/verify.py:load_rates` |
| Разрезы по отрасли, программе и просрочке складываются в портфель | `sql/90_checks.sql:segments_sum_to_total` |
| PAR90 входит в PAR30 и в NPL, провизии — от 1% до 50% портфеля | `sql/90_checks.sql:metric_bounds` |
| Каждая цифра выгрузки совпадает с независимым пересчётом из CSV | `scripts/verify.py:main` |
| Колонки семантических моделей существуют в витринах | `scripts/check_semantic.py:main` |
| Повторный запуск SQL ничего не ломает | `Makefile:check` — `load` дважды подряд |

## Что требует согласования

Меняется отдельной задачей, с описанием причины и последствий, а не по ходу другой работы:

- **Определения метрик и их толкование** — правятся одновременно в `sql/10_reporting.sql` и
  `scripts/verify.py`: это две реализации одних правил, и правку только одной ворота поймают.
- **Формат YAML** — формат заказчика: новые ключи не добавляются.
- **Проверки** — `sql/90_checks.sql`, `scripts/verify.py`, `scripts/check_semantic.py` не
  ослабляются ради зелёных ворот.

## Границы

- `data/` — исходники задания, руками не правятся (запрещено в `.claude/settings.json`). Аномалия
  в данных чинится правилом в витрине или записывается в README.
- Секретов в проекте нет: пароль `postgres` — локальный, только для контейнера.

## Сгенерированные файлы

Руками не правятся: их перезапишет ближайший прогон генератора. Правится источник.

- `dashboard/data/*.json` → `make export` (входит в `make check`)
- `docs/dashboard.png` → `make screenshot`

## Формат коммитов

Conventional Commits со скоупом: `тип(скоуп): что сделано`.

```
feat(sql): витрина концентрации по группам заёмщиков
fix(dashboard): подписи PAR30 и NPL не налезают друг на друга
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
Скоупы: `sql`, `semantic`, `dashboard`, `scripts`, `docs`.

Один коммит — один завершённый шаг; репозиторий остаётся рабочим после каждого.

## Язык

- **Комментарии в коде, тексты дашборда и документы** — русский. Комментарий пишется только для
  неочевидного «почему».
- **Сообщения коммитов** — тип и скоуп по-английски, описание по-русски: `feat(sql): …`.

## Журнал изменений

Всё, что видно снаружи, пишется в `## [Unreleased]` [CHANGELOG.md](CHANGELOG.md) **в том же
коммите**, что и правка. Решение, выбранное из нескольких вариантов, — ADR в
[docs/adr/](docs/adr/).

## Ссылки на код в документах

Называем символ — `путь/до/файла:имя`, а не номер строки: номер уезжает при первой правке выше по
файлу. В SQL символ — имя витрины или проверки (`check_name`).
